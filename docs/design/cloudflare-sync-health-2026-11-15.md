# Cloudflare 同步與節點健康

## 01 單項失敗繼續彙總

分組與節點批次同步逐項執行。單一成員同步失敗時保留該成員錯誤狀態並繼續處理後續成員；任務結果回報成功數與失敗數，避免已完成項目因批次中止而重複執行。

## 08 IPv6 雙棧

節點分組可為每個節點選填 IPv6。最低可用優先級的節點仍依原有多節點規則選擇，同一節點可同時建立受管 A 與 AAAA 記錄。自訂 A／AAAA／CNAME 目標維持原有語義。

受管記錄以成員、節點及記錄類型區分，舊資料空記錄類型按 A 解讀。

## 09 健康與防抖

節點必須有未逾時的心跳，且 OpenResty 不得回報 `unhealthy` 才能參與節點模式同步；狀態為 `offline` 的節點僅在防抖窗口內暫時保留。分組可設定 0 至 86400 秒防抖時間；短暫離線時在此窗口內仍保留節點，超過窗口才切換，0 維持立即切換的相容預設。

本次 migration 為 `00023_cloudflare_dual_stack_health.sql`，同時提供 PostgreSQL 與 SQLite。

### 事件同步與每 4 小時兜底

分組設定、成員新增／修改／移動、節點 IP 改變及手動同步沿用事件派送。心跳只在 IP 改變、離線恢復或 OpenResty 進出 `unhealthy` 狀態時觸發一次節點同步；同一心跳同時發生多項變化仍只派送一次，一般心跳不建立 Cloudflare 任務。

全量同步改為插件排程 `0 */4 * * *`，依排程器時區每 4 小時執行一次，用於修復遺漏事件、遠端 DNS 漂移及失敗任務。既有自動重試與手動同步保留。

為避免故障切換也被延後 4 小時，控制面每 30 秒進行本地健康檢查，不呼叫 Cloudflare API、不為每次檢查建立任務。只有已同步成員的可用節點集合或 IP 與已保存受管記錄不同時，才將成員原子標記為待同步並派送；多個控制面同時檢查時，只有成功取得該狀態的實例派送。派送失敗會恢復狀態，供下次檢查重試；待處理、執行中及錯誤成員交由既有重試與 4 小時兜底，避免重複排隊。

防抖沿用既有判定：`offline` 節點自最後心跳起在 `debounce_seconds` 窗口內保留；仍標示 `online` 但心跳超過 60 秒的節點，以及 OpenResty 明確回報 `unhealthy` 的節點不受此窗口保護。窗口到期或節點不可用後，下一次健康檢查選擇數字最小優先級的可用節點；同優先級可同時服務，恢復時可切回較高順位。沒有任何可用節點時保留遠端既有記錄，不清空 DNS。實際生效時間另受佇列執行與 DNS TTL 影響。

此排程與健康檢查調整不新增設定或資料表，也不修改歷史 migration；`00023` 是先前雙棧與健康欄位的遷移。
