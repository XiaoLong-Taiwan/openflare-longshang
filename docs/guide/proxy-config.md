# 新建反代配置

你会学到：如何一步一步在 OpenFlare 中从零新建并发布一个反向代理网站配置。本指南将指导你如何完成证书导入与申请、源站定义、路由规则配置、版本发布以及连通性验证。

---

## 推荐操作流程

在网关控制面中，建议遵循以下步骤新增反代规则：

```text
  [ 步骤 1. 证书管理 ] ──► [ 步骤 2. 源站定义（可选） ] ──► [ 步骤 3. 新增网站配置 ]
                                                                   │
  [ 步骤 5. 验证访问 ] ◄── [ 步骤 4. 发布与激活版本 ] ◄───────────────┘
```

---

## 第一步：证书准备

在使用 HTTPS 安全加密流量前，你需要先准备好对应的 TLS 证书（支持手动导入已有证书，或通过 DNS 验证自动向 CA 申请并托管续期）。

为了保持反代配置指南的简洁，证书相关的详细操作（包括如何在 Cloudflare 申请专用 DNS API Token）已独立拆分为专属指南。请先前往 **[TLS 证书与自动续期](./certificates.md)** 完成证书准备，然后回到这里继续下一步。

---

## 第二步：准备上游源站（可选）

源站（Origin）代表被代理的后端真实服务地址。虽然在新建网站时可以直接填写 IP，但推荐先在源站库中进行注册，以便后续复用与维护：

1. 进入左侧导航 **「网站管理」->「源站地址」**，点击 **「新增源站」**。
2. 填写源站名称（如 `production-api`）。
3. 填入合法的上游地址（如 `http://10.0.0.10:8080`），点击保存。

---

## 第三步：新建网站配置

证书和源站就绪后，即可创建核心网站代理路由：

1. 进入左侧导航 **「网站管理」->「域名列表」**，点击 **「新增 Zone」**，登记注册根域（如 `example.com`，不可填写 `*.example.com`）。进入该 Zone 的域名列表添加具体域名或通配符域名：
   * **域名**：输入 `api`、`@`、`*` 或完整名称（如 `*.s3.example.com`）。`*` 展开为 `*.example.com`，不支持 `*.s3` 简写。
   * **绑定证书**：选择第一步准备或申请好的证书。
2. 配置请求路由规则：进入 **「规则管理」** 页面，点击 **「新建规则」** 或编辑已有规则：
   * **规则名称**：输入规则的唯一简易标识（如 `app-portal-route`）。
   * **域名匹配**：从已登记域名中选择具体或通配符域名，也可通过「快捷新增域名」创建并绑定。
   * 在下方 **「反向代理」** 选项卡下，选择 **回源方式** 为「直连上游」。
   * **源站选择**：从下拉框中选择第二步创建的源站；或者选择手动输入并填入 `http://10.0.0.20:9000`。
3. 点击保存创建配置。

### HTTP/2 开关

规则详情的「反向代理」区域可单独开启或关闭 HTTP/2。此项控制客户端到网关的 HTTPS 连接，不改变回源协议，也不关闭独立的 HTTP/3 设置。保存后仍须发布并激活配置版本；普通反代、逐域名代理覆盖、Pages 与 Service Worker 分支均使用同一规则值。

新增规则默认开启；升级时 `00020_proxy_route_http2.sql` 为旧规则保留开启状态。旧客户端创建时省略 `enable_http2` 默认开启，更新时省略则保留当前值；旧配置快照没有此字段时也按开启处理。若要确认协商结果，可在支持 HTTP/2 的 curl 中运行 `curl --http2 -I https://your-domain.com`，同时检查节点已应用的配置中对应 `server` 块的 `http2 on` 或 `http2 off`。

### 通配符域名示例

要让 `bucket.s3.example.com` 等域名共用站点规则：

1. 在 `example.com` Zone 下添加 `*.s3.example.com` 并绑定路由；不需要逐个登记 bucket 域名。
2. 使用 HTTPS 时绑定 SAN 包含 `*.s3.example.com` 的证书。`*.example.com` 证书不能替代它；`*.s3.example.com` 证书也不覆盖 `s3.example.com` 或 `a.bucket.s3.example.com`。
3. 在 Cloudflare 分组中选择该通配符域名：节点模式跟随节点 IPv4 写 A 记录；自定义模式可写 A、AAAA 或 CNAME。DNS 同步与站点配置发布是两件事，须分别确认成功。
4. 按下一节发布并激活版本，Agent 会收到并渲染 `server_name *.s3.example.com;`。通配符沿用 Nginx 后缀匹配，可匹配多层子域名但不含后缀根自身；具体域名路由优先，重叠通配符以更长后缀优先。TLS 仍受上一条的单层证书覆盖限制。
5. 使用具体主机名访问验证，例如 `https://bucket.s3.example.com`，不要直接打开带 `*` 的地址。Zone 统计会聚合命中的实际 Host；Uptime Kuma 则需要至少绑定一个具体域名，否则跳过该路由的监控创建/更新并记录原因。

不允许 `foo*.example.com`、`a.*.example.com` 或多个 `*`；带协议、路径、端口、域名内部空白及非法 DNS 标签的输入也会被拒绝。

## 请求缓冲、响应串流与 Gzip

本地保留 `openresty_proxy_request_buffering_enabled=false`，即默认生成 `proxy_request_buffering off`，让请求正文可以边接收边转发，维持上传及请求串流的既有相容性。开启后，网关通常先完整读取请求正文再交给源站，可能增加首字节延迟及临时磁盘用量；适合需要隔离慢速上传的场景。可在「性能设置」全局开启，或在规则的反向代理设置中单独覆盖；未设置的规则继承全局值。已有的显式开关值不会被本次整合重写。

请求缓冲与响应缓冲是两个方向：SSE／模型逐字输出等响应串流应检查 `proxy_buffering`，不能仅靠关闭 `proxy_request_buffering` 保证。Nginx 对 HTTP/1.1 chunked 请求在未使用 HTTP/1.1 回源时仍可能缓冲，WAF 读取正文等处理也可能影响串流；请用真实上传／串流请求验证。

内建主配置模板新增 `gzip_vary on` 及文本、CSS、JavaScript、JSON、XML、RSS、Atom、SVG MIME 类型；`text/html` 由 Nginx 默认支持，不重复列入。是否压缩仍由 Gzip 开关、最小长度、客户端协商及源站响应决定，不添加 `text/event-stream`。这只是模板优化，不改变请求或响应缓冲开关。

未保存自定义主模板的环境会在下一次生成并发布配置版本时使用新模板；已有快照保持原内容。已保存的主模板（包括手动保存的旧默认模板）保持原样，如需启用相同优化，请自行合并上述两条 Gzip 指令，再预览、发布并验证。此次不修改数据库结构、初始化 seed 或自定义模板，不需要 migration。

## 第四步：发布并生效配置

你在管理端新增的网站配置仅保存在 Server 数据库中，**不会立即生效**。必须生成配置版本快照并分发到 Agent 边缘节点：

1. 点击控制面板右上角的 **「预览并发布」** 按钮。
2. 检查配置文件的 Diff 差异，确认你刚刚新增的 `server` 块以及证书绑定规则无误。
3. 点击 **「确认发布」** 按钮。
4. **Agent 落地机制**：
   * 数据面的 Agent 节点在心跳中发现激活的版本 Checksum 变更，会自动拉取完整的 OpenResty 配置文件和证书包到本地。
   * 自动在本地执行配置校验（类似于 `openresty -t`），确认无语法错误后，执行平滑重载（`reload`）。
   * 如果重载或校验失败，Agent 会安全阻断并回滚至上一稳定版本，保证节点高可用。

---

## 第五步：连通性与回滚验证

### 1. 验证访问
你可以通过以下方式验证新配置是否生效：
* **浏览器访问**：直接在浏览器输入 `https://your-domain.com` 查看是否成功代理后端。
* **命令行验证**（推荐）：使用 `curl` 探测：
  ```bash
  curl -I https://your-domain.com
  ```
* **绕过 DNS 校验**：若你的域名尚未正式解析，可以临时指定 `Host` 请求头请求 Agent 节点物理 IP：
  ```bash
  curl -I -H "Host: your-domain.com" https://AGENT_NODE_IP --insecure
  ```

### 2. 一键秒级回滚
如果发布的新配置导致了线上业务异常：
1. 导航至左侧 **「版本发布」** 菜单。
2. 在历史列表中找到发布前的上一个稳定版本。
3. 点击 **「激活」**。
4. 所有在线 Agent 节点将在秒级自动重载回历史配置，实现秒级避险。

## 边缘缓存（可选）

站点详情 **「缓存」** 页可开启边缘 `proxy_cache`（须同时开启 **性能设置 → 全局 OpenResty 缓存**）。行为对标 Cloudflare 默认模型，详见 [边缘缓存策略设计](../design/edge-cache-design.md)。

### 推荐设置

| 项 | 建议 |
| --- | --- |
| 策略 | **标准静态资源**（默认推荐）：仅 css/js/map/图片/字体等，**不含 HTML/JSON** |
| 登录 Cookie | **不会**单独跳过缓存；带会话的用户仍可命中静态资源 |
| 源站 | 静态资源建议 `Cache-Control: public, max-age=…`；动态/个性化必须 `private` 或 `no-store` |
| 响应 Set-Cookie | 不会写入边缘缓存 |
| 无源站缓存头 | 按状态码使用默认 Edge TTL（如 200 约 120 分钟） |

### 高级策略「所有可缓存 GET」

类似 Cloudflare Cache Everything：路径不再限制扩展名。若源站对 HTML 未声明 `private`/`no-store`，**可能把个性化页面缓存并串用户**。仅在源站缓存头正确、或内容全局一致时使用。

### 每条规则的高级 Nginx 缓存参数

每条代理规则可在 **「缓存 → 高级 Nginx 缓存参数」** 独立覆盖以下行为：

- 为成功响应、重定向响应和未找到响应设置不同的 Edge TTL，例如 `2h`、`30m`、`1m`。
- 请求携带 `Authorization` 时绕过缓存。
- 按 Cookie 名称设置绕过名单，避免会话请求读取或写入共享缓存。

高级参数使用结构化白名单并在服务端验证，不支持直接输入任意 Nginx 指令，也不会绕过源站 `Set-Cookie`、`private` 或 `no-store` 等隐私保护。

### 生效方式

缓存开关与策略写在配置快照中。保存站点后须 **发布并激活配置版本**，Agent 应用后才生效。仅改 UI 不发布则节点仍用旧规则。

### 快速自检

1. 全局缓存已开，站点缓存已开，策略为「标准静态资源」。  
2. 发布配置并确认节点应用成功。  
3. 带登录 Cookie 连续两次请求同一 `/assets/app.js`（或带 hash 的 immutable 路径），访问日志中 `cache_status` 第二次应为 **HIT**（或 UI「命中」）。  
4. 若仍为「未缓存」：确认策略是否匹配该路径扩展名、是否非 GET、源站是否返回 `Set-Cookie` / `private`，以及节点是否已应用新版本。更多见 [故障排查 · 边缘缓存](./troubleshooting.md#边缘缓存命中率异常)。
